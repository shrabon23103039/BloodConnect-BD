# 14 — Academic SDLC and Formal 16-Week Work Plan

## 1. Methodology

BloodConnect BD follows an iterative and incremental SDLC with Agile Scrum-inspired planning. Work is organized into short iterations, with review and testing at the end of each increment.

The formal methodology describes the engineering process. Actual project dates, implementation effort and test outcomes must be reported truthfully in the final report.

## 2. SDLC phases

1. Initiation and feasibility.
2. Requirements engineering.
3. System analysis and design.
4. Implementation.
5. Verification and validation.
6. Deployment.
7. Maintenance and evaluation.

## 3. Formal 16-week schedule

| Weeks | Phase | Deliverables |
|---|---|---|
| 1 | Initiation/planning | Proposal, scope, feasibility, risks |
| 2–3 | Requirements | Stakeholders, use cases, SRS |
| 4–5 | Design | Architecture, UML, ERD, UI spec |
| 6–9 | Core implementation | Accounts, donor, search, request workflows |
| 10–11 | Advanced implementation | Contact, notifications, moderation, analytics |
| 12–13 | QA | Functional, security, integration and performance testing |
| 14 | Deployment | Staging/production configuration and smoke tests |
| 15–16 | Documentation/evaluation | Final report, user guide, demo, viva |

## 4. Agile roles for individual project

As an individual project, one student performs the responsibilities of:
- Product Owner: scope and prioritization.
- Scrum Master: iteration planning and review.
- Developer: implementation.
- QA: test design and verification.
- Release Manager: deployment and release notes.

The project may receive feedback from supervisor/users as available.

## 5. Iteration structure

Each iteration:
1. Select tasks from backlog.
2. Confirm acceptance criteria.
3. Design/implement.
4. Test.
5. Review the increment.
6. Record defects and decisions.
7. Update backlog and documentation.

## 6. Feasibility analysis

### Technical
Django, PostgreSQL and Bootstrap are established technologies. The MVP does not require government APIs or hospital partnerships.

### Operational
Donors and recipients can use the platform through a browser. Moderation and support processes are needed before public launch.

### Economic
The MVP can be developed using open-source frameworks. Hosting, SMS, email, domain, monitoring and storage may introduce operating costs.

### Schedule
The 16-week academic plan allows requirements, design, implementation, testing and documentation. A shorter internal build target does not remove the need for verification.

### Legal and ethical
Public launch requires local legal, privacy and healthcare review. The platform must not operate as an unlicensed blood bank or clinical service.

## 7. Evaluation criteria

- Requirements traceability.
- Functional completeness.
- Correct authorization and privacy.
- Usability and accessibility.
- Test coverage and defect resolution.
- Deployment repeatability.
- Measured performance.
- Quality of technical documentation.
- Ability to explain design decisions in viva.

## 8. Reporting integrity

Do not state that tasks were completed during weeks in which they did not occur. A formal schedule is a plan, not evidence of historical work. Report actual implementation dates and test results in the final report.
